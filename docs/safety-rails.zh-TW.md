# 安全防護機制（獨立於 LLM）

預設值在 [README](../README.zh-TW.md) 的產生表格裡，不要手動改那張表。

那張表是產生出來的，不是手打的：`tools/readme_rails.py` 用 `ast` 解析 `trader.py`，重寫 `RAILS` 標記之間的區塊。提交前先跑 `--check`（有漂移就 exit 1），要重新產生則用 `--write`。它讀 AST 而不是對原始碼做 grep，因為 regex 分不出被註解掉的呼叫、兩個預設值不同的呼叫會默默取第一個、而且遇到非字串字面值的預設值就整個放棄 —— 每一種情況都可能發布出一個程式根本沒在用的數字。同一個變數被讀兩次卻給出不同預設值，會被視為錯誤，不會隨便挑一個。這個專案過去發布出去的每一個過期數字 —— GitHub 主頁寫死的 `/20`、儀表板頁尾手寫的模型清單 —— 都是某個被抄過去的值。抄寫本身就是 bug，推導才是解法。

信心度低於門檻的 BUY 或 SELL 會被否決並記下理由，跟 Haiku 否決或情緒指標牴觸的處理方式相同。這一條刻意不提供環境變數覆寫：量過這隻機器人自己的歷史後發現，信心度分數對結果沒有預測力，所以它只留著當一道粗略的門檻，不拿來當排序依據。

倉位規模是*投資組合總值*的百分比，這個數字完全不反映已交割的現金。在加入**現金防護**之前，`MAX_POSITIONS x POSITION_SIZE_PCT <= 100%` 是唯一阻止機器人動用融資的機制 —— 而模擬帳戶通常配有約 4 倍的購買力，因此超出預算的訂單不會失敗，而是靜靜地用借來的錢成交。`execute_trades()` 現在會在整輪執行中追蹤可動用現金，把訂單裁切到現金足以支應的數量，並在現金耗盡時記錄 `SKIPPED_CASH`。前一輪遺留的未成交買單會先從現金與持倉槽兩邊的預算扣掉，再重新分配，因為 Alpaca 是在成交時才扣現金，不是送單時。賣出會排在買入之前處理，所得再回補，讓滿倉狀態仍能換股；裁切後低於 `MIN_TRADE_USD` 的單會直接跳過，不讓零碎部位佔掉一個持倉槽。

**移動停損**要等倉位的即時高點比進場價多漲 `TRAIL_ACTIVATE_PCT` 之後才會啟動，之後從那個高點回檔 `TRAIL_STOP_PCT` 就出場 —— 在獲利標的上鎖住收益，同時保留強制停損底線來管那些從頭到尾沒漲上去的標的。高點紀錄存在 `trade_logs/position_peaks.json`，每次執行都會取樣。
